v2.1.1 (nightly)
  - Fixed the "grey fade" on every page besides the dashboard (list/web, list/user, list/mail, list/db, and every other page that uses Hestia's standard list/toolbar UI). Root cause: cpanel_theme's 5 color CSS files were built by reusing dark_glass_theme's shared component-rules template verbatim, which includes two rules - .toolbar (the search/filter/add bar above every list) and .units-table-header (every table's column-header row) - with a hardcoded dark gradient background (linear-gradient(#3f3b3b...)) instead of a theme variable. That's the right call for a dark glass theme but produces a jarring dark-grey bar on cpanel_theme's white/light-gray pages, on what's most of Hestia's actual page surface - the dashboard was the only page that avoided it, since it's the only page that doesn't use those two classes. Rebuilt all 5 cpanel_theme color files with a cpanel-specific version of the component template where both rules use var(--bg-glass)/var(--bg-glass-light) and var(--border-glass) instead, matching the white panel look everywhere else in the theme.
  - Reworked cpanel_theme's dashboard into a two-column layout (Tools | General Information), matching real cPanel's Home page more closely: shrank the oversized "Dashboard" title, removed the Quick Stats row (Uptime/Server Time/CPU/RAM) and the 6 resource cards (Users/Web Domains/Mail Accounts/Databases/Cron Jobs/Disk Usage) along with the Recent Activity/System Status section, and replaced them with a narrower right-hand column showing General Information (current user, primary domain, SSL certificate status, IP address, last login IP) and a Statistics panel of label/value rows. Note the exact Statistics list requested (Addon Domains, Subdomains, Mailing Lists, Autoresponders, Forwarders, Email Filters, separate MySQL/PostgreSQL database and disk-usage counts) is cPanel/WHM-specific - Hestia doesn't track any of those as distinct features, so the Statistics panel instead uses Hestia's real equivalents (Disk Usage, Bandwidth, Web Domains, Domain Aliases, Email Accounts, Mail Domains, Databases, DNS Zones, Cron Jobs) rather than showing fabricated always-zero rows for things Hestia can't actually do.
  - dashboard_index.php (the shared /list/dashboard/ controller used by every Dashboard Theme, not just cpanel_theme) now also fetches the account's primary web domain, its SSL status, and its IP via one extra v-list-web-domains call, feeding cpanel_theme's new General Information panel. Harmless no-op for the other themes, which don't reference the new variables.
  - Fixed cpanel_theme's sidebar and rebuilt its dashboard as a real cPanel-style tools grid, after feedback that the sidebar stayed permanently open/never collapsed and the dashboard didn't look like cPanel's actual Home page (a screenshot of the real page - white category panels each holding a wrapped grid of icon+label items for Email/Files/Databases/etc - was provided for reference). Real cPanel has no persistent left sidebar at all in this view, so the sidebar is now a fully hidden off-canvas drawer at every screen width (transform: translateX(-100%) by default) instead of the permanent hover-expanding icon rail dark_glass_theme uses - a menu button now lives in the top bar (always visible, not just on mobile) and toggles it open as an overlay via the same CSS-only checkbox mechanism, closing again on an overlay click. Also fixed the overlay backdrop itself never being able to show at all: it had `display: none` as a base rule with only opacity/visibility toggled on :checked, and display:none can't participate in a CSS transition or be overridden by a sibling selector that never touches display - switched to opacity/visibility/pointer-events throughout so it actually fades in/out and blocks clicks correctly.
  - Replaced list_dashboard.php's single-row "Quick Actions" section with a categorized tools grid (Files/Databases/Domains/Email/Metrics/Security/Advanced/Preferences), each a white panel with a colored category icon header and a wrapped grid of icon+label items linking to the real Hestia pages - directly mirroring real cPanel's Home page structure. Item/category icon colors pull from each Color Theme's existing --icon-color-* variables, so the 5 color options extend into the tools grid too. Kept the existing stats cards/activity/status sections as-is since they show real live data cPanel's static tool list doesn't have an equivalent for.
  - Redesigned cpanel_theme to actually match cPanel's real look after feedback that the first pass (a generic light flat theme) didn't. Pulled the real Jupiter theme's CSS from a live cPanel demo instance and used its actual --cp-* custom-property palette (dark navy #08193e text/brand, white #fff surfaces, light gray #f7f8fa page background, indigo #4259ed primary action color, plus the real semantic colors: success #218838, warning #ffc107, error #dc3545, info #138496) instead of guessed values. Two structural fixes that matter more than color: added a real fixed top bar (cp-topbar in header.php - logo/app name left, current username right, hidden on the login page since there's no session user yet) since Hestia's page shell had no header bar at all before, and made the sidebar a fixed dark navy (#08193e) with light gray text instead of white - the single biggest visual signature the first attempt got backwards. Sidebar color is now a hardcoded brand constant matching how cPanel itself works (only the accent color changes between its theme options, not the whole sidebar), with the 5 Color Theme variants instead varying --color-text-link/accent throughout (indigo default, plus teal/slate/green/graphite alternates) and active/hover nav items picking up the accent color as a left-border highlight. Had to bump selector specificity on the sidebar/submenu background rules (.app2 .sidebar, .sidebar .sidebar-submenu) since the color theme file's own lower-specificity rules load after style.css and would otherwise silently override the hardcoded navy with the color file's white --bg-glass.
  - Added 5 new Color Theme variants to dark_glass_theme (emerald, crimson, ocean, amethyst, sunset), generated from the existing dark_glass_theme_color.css/orange_color_theme.css pattern where every color variant is byte-identical except for its :root custom-property block - confirmed via diff before deploying. Registered all 5 in theme.json's whitelist.
  - Added 5 new Color Theme variants to glass_theme (sunrise, forest, berry, slate, violet) using the same :root-swap pattern, using the --hestia-* variable set that glass_theme's style.css actually references. Registered all 5 in theme.json.
  - Fixed glass_theme's declared default Color Theme ("glass_theme_color") never actually existing as a deployed file: its real source was css/color_theme.css, but that exact filename is on install_theme_css_files()'s permanent skip-list (it's treated as a per-theme *template* to derive variants from, not something deployed directly - same convention dark_glass_theme already followed). Copied its content to the properly-named glass_theme_color.css; verified byte-identical to the original source before deploying.
  - Added a new cPanel-styled Dashboard Theme (cpanel_theme) with 5 Color Theme variants (classic_blue, jupiter_teal, slate_gray, forest_green, graphite). Cloned dark_glass_theme's PHP structure as-is (same page templates, same class names - only CSS changed, so no PHP changes were needed beyond includes/css.php's image-path rewrite target). Rewrote css/style.css to drop the glassmorphism look (backdrop-filter blur, floaty hover lifts, 16-20px bubble radii) in favor of flat white cards, 6-8px corners, a classic sans-serif stack, and a solid page background - same selectors throughout, so it's a drop-in replacement.
  - Fixed a bug caught during pre-deploy verification (not live yet at the time): the shared "component rules" fragment used as a template for all 10 new dark_glass_theme/cpanel_theme color CSS files was extracted with `sed -n '211,758p'`, where 758 came from `wc -l` - but the source file's last line (a lone "}" closing the @media print block) has no trailing newline, so wc -l undercounted by one and silently excluded it. Every generated file was missing its final closing brace. Caught by a brace-balance check (124 open vs 123 close) before anything was left live; re-extracted with `sed -n '211,$p'` instead, rebuilt all 10 files, and redeployed.
  - Fixed a real bug found by actually running uninstall.sh then install.sh end-to-end against a live server: switching Dashboard Theme (or uninstalling) changes what web/templates resolves to, but PHP-FPM workers are long-lived and cache resolved symlink paths in their own realpath_cache (default TTL 120s) independently per worker. Nothing ever told PHP-FPM to drop that cache, so for up to two minutes after either operation, whichever worker handled a given request could still resolve paths against the *previous* target - which had often just been deleted - causing a fatal "failed opening required .../header.php" 500 on an otherwise completely correct file structure. This wasn't just an uninstall edge case: it affected the live Dashboard Theme dropdown too. hestia_theme_manager.php now sends a graceful reload (SIGUSR2, no dropped connections) to hestia-php after both applyThemeSymlinks() and restoreOriginalTemplates().
  - Fixed install.sh capturing an already-patched panel.php/edit_server.php as the plugin's "pristine original" template backup: run_plugin_install() (which snapshots web/templates/ for a future uninstall to restore from) ran *after* apply_patch_files() had already modified two files inside that same directory. Reordered so the plugin's own install step - and the directory copy that feeds it - runs before any patching touches web/templates/.
  - Public-release hardening pass on install.sh/uninstall.sh, from a full logic + security review:
    - backup_original_files() was not idempotent: re-running install.sh (updates, retries) silently overwrote the true original-file backups with whatever was currently live - which by then was already our own patched version. uninstall.sh would then "restore" patched files onto themselves instead of reverting to stock Hestia. It now skips any backup that already exists.
    - THEME_DIR was accidentally shadowed: the global (/usr/local/hestia/web/themes, the "active" theme) was silently reassigned inside create_theme() to a different path (/usr/local/hestia/web/list/theme, the gallery), and later code relied on that accidental value without realizing it. Split into two properly-named variables, THEME_DIR and GALLERY_DIR, used explicitly and consistently.
    - install_theme_css_files()'s file-count summary always reported "No theme CSS files were found" even after successfully installing dozens - the counter was incremented inside a `find | while` loop, which bash runs in a subshell, so the increments never reached the outer scope. Switched to process substitution.
    - Two spots (install.sh's run_plugin_install, uninstall.sh's restore_original_theme) checked a command's result via a separate `[ $? -eq 0 ]` after the fact instead of using the command directly as the if-condition. Under `set -e`, a failing command exits the script immediately before that check is ever reached - in uninstall.sh's case, this meant the manual-restore fallback would never actually run if the primary restore failed.
    - Backup directories written to /tmp (install.sh on reinstall, uninstall.sh's theme backup) are now chmod 700. Hestia is a multi-tenant host by design - /tmp is shared across every local user on the box, so a world-readable backup directory sitting there is readable by other tenants' shell users.
    - configure_sudo_permissions() now fails loudly if the expected hestiaweb user doesn't exist, instead of silently granting root-via-sudo access to a guessed www-data fallback that might be an unrelated, differently-privileged user on a non-standard install.
  - Fixed Color Theme selection not visibly applying (most noticeable with maxtheme's variants). Root cause: hestia-theme css (run via CLI/sudo so it can persist to hestia.conf) correctly saved the new server-wide default, but couldn't touch the *current* browser session's $_SESSION - and includes/css.php always prefers a personal $_SESSION["userTheme"] override over the server default, so anyone with a personal theme set (which by this point was most accounts, from earlier per-user testing) just wouldn't see the change. dashboard_toggle.php now also updates $_SESSION directly after a successful change, for both the server-wide (Configure Server) and per-user (Edit User, when editing your own account) cases.
  - Removed the /list/themes/ workaround page (theme_index.php + list_themes.php) and its "Themes" sidebar link in all three themes. It was a manually-duplicated copy of theme_index.php (the sidebar always linked to /list/themes/ plural, but install.sh only ever created /list/theme/ singular) working around the old picker; Dashboard Theme and Color Theme now live directly on Configure Server and Edit User, so it's no longer needed. install.sh no longer installs it; uninstall.sh cleans up the plural duplicate directory on old installs.
  - Fixed "Internal Server Error" followed by "Potential CSRF use detected" when changing the Color Theme. Root cause: Hestia's own edit/server/index.php and edit/user/index.php controllers check `$_POST["v_theme"]`/`$_POST["v_user_theme"]` unconditionally on every page load, GET or POST. On PHP 8.3 that's a fatal TypeError as soon as $_SESSION["THEME"]/userTheme holds a real value (null can no longer implicitly coerce into quoteshellarg()'s string param) - and our theme picker keeps that session value populated far more often than stock Hestia would, so the crash became easy to hit: change the color theme, the page reloads, the reload itself 500s. Guarded both checks with !empty(); install.sh now patches this in-place (targeted sed, not a full file copy, since these controllers are large and move fast between Hestia releases) and uninstall.sh restores the originals.
  - Fixed dashboard/theme pages rendering as a mix of default Hestia styling and the theme's look, missing card/grid layout entirely. Root cause: each theme's style.css (the structural stylesheet) was being linked as /templates/css/style.css, a URL the panel's own nginx config blanket-blocks (everything under /templates/ 404s, to stop .php source files from being downloaded). Only the color-theme CSS was ever actually reaching the browser.
  - Fixed by having includes/css.php read style.css directly off disk (through the templates symlink, same as how header.php already loads css.php/js.php/title.php themselves) and inline it in a <style> block, instead of linking to it as a URL. Never touches nginx - the panel's config is untouched.
  - Also fixed the active dark_glass_theme's includes/css.php, which was separately missing the style.css include entirely (a second, unrelated bug stacked on top of the nginx-blocked-URL one)
